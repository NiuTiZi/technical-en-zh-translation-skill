# 英译中写作规范

本规范用于技术及其他专业文档。先准确复现原意，再让中文易读；具体词条见通用词库与相关领域词库。

## 1. 信息与语气

- 保留原文的事实、因果、时间顺序、条件、例外、否定和不确定性。`may`、`might`、`can`、`must`、`should`、`shall` 不要一律译成“可以”或“必须”；结合规范性语境判断“可能”“可以”“应”“必须”等。
- 不擅自补充版本、性能、安全性或兼容性结论。原文有疑似错误时，忠实翻译并在确有必要时附简短译者注。
- 把英文长句按逻辑拆分，主语和指代要清楚，但不要改变条件的作用范围。
- 保持原文的人称和语气：步骤说明可以用祈使句；规范和警告应清楚直接。避免“进行一个……的操作”等冗余表达。

## 2. 术语与首次出现

- 先判断词义，再按 [`SKILL.md`](../SKILL.md) 的优先级选择译法。同一概念在同一文档中尽量一致；不同概念即使英文同形也不能强行统一。
- 有成熟中文译法、但读者可能需要核对英文的关键术语，首次出现可采用“中文（English）”，如“检索增强生成（Retrieval-Augmented Generation，RAG）”。后续使用中文或通行缩写。
- 产品、项目、标准、协议缩写及行业中习惯保留的英文词，通常保留原样。是否保留 `Token`、`Agent`、`Prompt` 等取决于目标读者和上下文；不要把示例词条当作全局禁译表。
- 英文大小写仅在专名、标识符和约定缩写中保持。一般名词按自然中文行文处理。

## 3. 不可改动的内容

默认原样保留以下内容及其内部空格、大小写、标点：

- 行内代码和代码块；Shell、PowerShell、Python、SQL 等命令与参数。
- API、函数、类、方法、包、字段、JSON/YAML key、HTTP Header、环境变量、文件名与路径。
- URL、域名、IP 地址、端口号、注册表路径、CVE 编号、哈希、日志字段和占位符（如 `<token>`、`${HOME}`）。
- 协议缩写及版本号，如 `JWT`、`OAuth 2.0`、`HTTP/2`。

代码块中的注释和字符串也默认保留；仅在用户明确要求时翻译其自然语言内容，并确保代码仍有效。正文中引用的标识符建议用反引号包围，避免与汉字黏连。

## 4. 结构与格式

- 尽量保留标题层级、段落、列表顺序、表格列、引用、注释标记和代码围栏语言标记。
- Markdown 链接的可见文字可翻译；目标 URL、锚点和引用标识保持不变。图片替代文本可翻译，但路径不变。
- 表格单元格内的术语按相同规则翻译。不要擅自合并行列或更改代码示例。
- 数字、单位、版本号、日期和比较符号保持准确。可按中文习惯调整空格和标点，但不可改变数值或单位。`MB` 与 `MiB`、`ms` 与 `s` 不可混淆。

## 5. 中文表达

- 用符合中文技术文档的语序和动词，如“签发 Token”“验证凭证”“部署工作负载”。避免逐词照搬英语被动句。
- 采用简体中文及一致的中文标点。英文标识符内部的标点、路径分隔符和命令引号保持原样。
- 首次出现的缩写可在原文有展开、或确有助于理解时补充中文释义；不要凭猜测展开未知缩写。
- 如果原文故意区分 `authentication` 与 `authorization`、`encoding` 与 `encryption`、`availability` 与 `reliability`，译文也应区分。

## 6. 译者注的边界

默认只输出译文。遇到确实会影响理解的歧义、明显源文错误，或同级词库冲突且无法从上下文消解时，可在译文末尾加简短“译者注”。说明不确定点和可能解释，不要把猜测写进正文。用户要求纯译文时，优先通过保留英文或中性表达避免擅自定论。

## 7. 交付前检查

对照原文核查：是否漏译；条件/否定/权限边界是否改变；相同概念是否使用一致译法；术语是否符合当前语境；代码和标识符是否逐字保留；Markdown 是否仍可阅读。
